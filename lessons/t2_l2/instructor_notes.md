# Instructor notes — T2.L2

## 1. Методичний задум

Це заняття має показати транспортну задачу не як «класичну таблицю з підручника», а як повний computational modeling workflow.

Основний акцент: **не solver, а структура моделі та доказовість результату.**

Ад’юнкт має вийти із заняття з розумінням, що CSV — це вхідні дані, DataFrame — представлення даних, LP formulation — модель, PuLP — інструмент реалізації, оптимальний план — результат моделі, feasibility check — перевірка математичної коректності, scenario analysis — дослідження властивостей моделі, а предметна інтерпретація — науковий висновок.

## 2. Рекомендована логіка проведення

### Етап 1. Постановка — 10–15 хв

Показати таблиці запасів, потреб та вартостей без коду.

Питання: **якщо на кожному маршруті є своя ціна, чи достатньо завжди вибирати локально найдешевший маршрут?**

### Етап 2. Формалізація — 20 хв

Разом визначити `x_ij`, `c_ij`, `a_i`, `b_j`, цільову функцію, row constraints та column constraints.

Особливо показати різницю між `Σ_j x_ij = a_i` та `Σ_j x_ij <= a_i`. У базовій збалансованій постановці ми плануємо розподілити весь наявний ресурс.

### Етап 3. Дані → Python — 15 хв

Відкрити CSV і показати, що структура індексів має відповідати математичним множинам. Принцип: **назви рядків і стовпців є частиною семантики моделі.**

### Етап 4. PuLP — 25 хв

Пояснити `LpProblem(..., LpMinimize)`, змінні `x[i,j]` та буквальний перехід математичних сум у `lpSum`. Не заглиблюватися в алгоритм simplex/CBC на цьому занятті.

### Етап 5. Verification — 15 хв

Після статусу `Optimal` запитати: **чи вже можна довіряти результату?**

Перевірити row sums, column sums, non-negativity і total cost. Потім показати independent solver verification через SciPy.

### Етап 6. Scenario — 20 хв

Закрити `S2 → D3`. До запуску попросити спрогнозувати, чи зміниться план, чи зросте вартість і які потоки можуть перебудуватися.

Після запуску: **515 → 570**.

Головне питання: **чому один маршрут виявився системно важливим?**

### Етап 7. Research transfer — 15 хв

Не вимагати від усіх буквальної логістичної задачі. Підказати абстрактну структуру: джерела інформації → аналітичні вузли; обчислювальні ресурси → задачі; викладачі/експерти → навчальні активності; сенсори → центри обробки; набори даних → дослідницькі процедури.

## 3. Контрольні результати

Baseline:

```text
        D1   D2   D3   D4
S1      30    5    0    0
S2       0   20   30    0
S3       0    0    5   35
```

**Z*=515.**

Route closure `S2 → D3`:

```text
        D1   D2   D3   D4
S1      30    0    0    5
S2       0   25    0   25
S3       0    0   35    5
```

**Z*=570.**

Якщо ці результати не відтворюються — перевірити дані, індекси, обмеження та версію задачі.

## 4. Типові помилки

1. **«Оптимальний» = «правильний».** Solver оптимізує записану модель; він може ідеально розв’язати неправильну постановку.
2. **Плутанина між cost і flow.** `c_ij` — параметр, `x_ij` — змінна рішення.
3. **Втрата балансу.** Зміна demand в одному пункті без компенсації створює іншу математичну постановку.
4. **Висновок лише з числа 515.** Треба пояснювати структуру потоків.
5. **Heatmap без питання.** Графік має показувати концентрацію потоків, зміну сценарію або критичні маршрути.

## 5. Дискусійні питання

1. Чи може існувати декілька різних оптимальних планів з однаковою вартістю?
2. Коли варто замінити рівність запасів на нерівність?
3. Як у модель додати пропускну здатність маршруту?
4. Як врахувати час доставки?
5. Як врахувати ризик маршруту?
6. Що робити, якщо попит випадковий?
7. Чим multi-objective transportation problem відрізнятиметься від базової?
8. Чи завжди «вартість» має бути грошовою?

## 6. Розширення для сильнішої групи

Можна запропонувати route capacity constraints, dummy supplier/consumer, integer flows, fixed route activation costs, двокритеріальну модель «вартість + ризик», Monte Carlo для невизначеного попиту або network visualization через NetworkX.

Ці елементи не є обов’язковими для базового T2.L2, щоб не перетворити одне заняття на окремий курс operations research.
