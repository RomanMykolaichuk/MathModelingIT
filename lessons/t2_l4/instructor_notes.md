# Instructor Notes — T2.L4

## Методична ідея

Це заняття не слід перетворювати на урок «як намалювати граф у NetworkX». Центральне питання:

> Які залежності між роботами реально визначають строк і ризик завершення складного процесу?

## Рекомендований хід

### 1. Словесний процес → граф

Спочатку показати таблицю `tasks.csv` без Python.

Запитати:

- які роботи можуть стартувати одночасно;
- що блокує E;
- який шлях здається найдовшим візуально.

Після цього виконати CPM.

### 2. Пояснити four timestamps

Не давати ES/EF/LS/LF як механічні формули.

- forward pass відповідає: **як рано це може відбутися?**
- backward pass: **як пізно це може відбутися без зміни project finish?**

### 3. Slack як управлінський зміст

Порівняти:

- C +3 → project +3;
- D +3 → project +0.

Саме тут стає зрозуміло, навіщо потрібна мережна модель.

### 4. Не ототожнювати critical task із «важливою роботою»

Critical у CPM означає zero scheduling slack. Це не оцінка військової, організаційної або наукової важливості.

### 5. Перехід до PERT

Запитання:

> Звідки взялося «C триває рівно 5»?

Показати, що реальні тривалості є оцінками.

### 6. Monte Carlo

Ключовий перехід:

**один CPM plan → distribution of possible project durations**.

Контрольні значення при `n=3000`, `seed=2026`:

- mean ≈ 17.86;
- P90 ≈ 19.69;
- P(T≤19) ≈ 0.79.

Не вимагати абсолютно однакових значень за іншого seed/n.

## Типові помилки

1. Вважати найдовшу окрему роботу критичною.
2. Ігнорувати паралельність.
3. Будувати циклічний граф.
4. Плутати task duration з calendar date.
5. Трактувати PERT numbers як «об’єктивну істину».
6. Стверджувати, що 0.79 — фактична ймовірність реального проєкту без валідації вхідних розподілів.
7. Не перевіряти зміну critical path у Monte Carlo.

## Дискусійне питання

Якщо Monte Carlo показує 79% шанс завершити до 19, чи є це достатнім для прийняття рішення?

Правильної універсальної відповіді немає: потрібен контекст, ціна запізнення і допустимий ризик.
