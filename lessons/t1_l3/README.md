## 4. Прикладна постановка

Досліджується умовна система, результативність якої залежить від доступного ресурсу `R`, навантаження `L`, параметрів математичної моделі та випадкової варіабельності спостережень.

Research question:

> Як змінюється очікувана результативність системи при зміні ресурсу або навантаження, і як організувати цей експеримент так, щоб його можна було точно повторити?

Кейс навмисно простий математично: основний предмет заняття — **організація дослідження**.

## 5. Математична модель

Детермінована частина:

\[
Y=\max(0,\;b+\alpha R-\beta L)
\]

де:

- `Y` — модельована результативність;
- `R` — ресурс;
- `L` — навантаження;
- `b` — базовий рівень;
- `α` — ефект одиниці ресурсу;
- `β` — штраф за одиницю навантаження.

Для baseline:

\[
b=20,\quad \alpha=1.8,\quad \beta=1.2.
\]

При `R=40`, `L=50`:

\[
Y=20+1.8\cdot40-1.2\cdot50=32.
\]

Стохастичне спостереження:

\[
Y^{obs}=\max(0,Y+\varepsilon), \qquad \varepsilon\sim N(0,\sigma^2),\quad \sigma=4.
\]

Стохастична частина потрібна для демонстрації `seed`, repeated runs, розподілу результатів та фіксації параметрів експерименту.

## 6. Припущення та межі застосовності

Модель припускає:

1. лінійний вплив ресурсу;
2. лінійний негативний вплив навантаження;
3. сталі параметри протягом експерименту;
4. нормально розподілену випадкову складову;
5. відсутність взаємодії між `resource` та `load`;
6. незалежність повторних реалізацій.

Модель **не доводить**, що реальна система має саме такі залежності.

> Відтворюваність неправильного припущення не робить модель адекватною.

## 8. Конфігурація експерименту

`experiment_config.json`:

```json
{
  "seed": 2026,
  "replications": 200,
  "model": {
    "baseline": 20.0,
    "resource_gain": 1.8,
    "load_penalty": 1.2,
    "noise_sd": 4.0
  }
}
```

Це дозволяє змінювати параметри експерименту без редагування математичної функції.

## 9. Сценарії

`data/scenarios.csv` містить п’ять сценаріїв:

| scenario | resource | load |
|---|---:|---:|
| baseline | 40 | 50 |
| resource_low | 30 | 50 |
| resource_high | 50 | 50 |
| load_low | 40 | 35 |
| load_high | 40 | 65 |

Для кожного сценарію виконується `200` стохастичних реалізацій.

## 10. Python workflow

`src/model.py` містить:

- `deterministic_response(...)`;
- `simulate_observation(...)`.

`src/experiment.py`:

1. читає JSON config;
2. читає CSV scenarios;
3. перевіряє конфігурацію;
4. запускає всі повтори;
5. формує raw results;
6. агрегує summary;
7. створює metadata;
8. зберігає outputs.

Запуск із кореня репозиторію:

```bash
python -m lessons.t1_l3.src.experiment
```

## 11. Контрольні результати

Для `seed=2026` і `200` повторів:

| Сценарій | Детермінований Y | Середнє спостережене Y |
|---|---:|---:|
| baseline | 32.0 | ≈32.29 |
| resource_low | 14.0 | ≈14.07 |
| resource_high | 50.0 | ≈50.11 |
| load_low | 50.0 | ≈50.16 |
| load_high | 14.0 | ≈13.78 |

`resource_high` і `load_low` дають однаковий детермінований результат `50`, хоча описують різні зміни системи. Однакове число не означає однаковий механізм.

## 12. Metadata та experiment identity

Для поточної конфігурації формується:

```text
experiment_id = t1_l3_0c5d08ed47eb
```

ID базується на SHA-256 hash канонічного JSON config.

`metadata.json` містить:

- experiment ID;
- config hash;
- seed;
- кількість повторів;
- кількість сценаріїв;
- параметри моделі.

Самого config hash недостатньо для абсолютної відтворюваності: потрібно також зафіксувати код, дані та software environment.

## 13. Verification / sanity checks

Перевіряються:

1. ручний випадок `R=40`, `L=50` → `Y=32`;
2. результат не може бути від’ємним;
3. однаковий seed відтворює stochastic run;
4. кількість рядків дорівнює `scenario_count × replications`;
5. config hash стабільний до порядку ключів;
6. metadata ідентифікує експеримент;
7. повторний повний запуск дає ідентичні raw results.

```bash
pytest lessons/t1_l3/tests -q
```

Контрольний стан: **9 passed**.

## 14. Що означає reproducibility

Для цього курсу reproducible computational experiment — це експеримент, який інший дослідник може повторити, маючи:

- код;
- вхідні дані;
- конфігурацію;
- software dependencies;
- seed, якщо є випадковість;
- інструкцію запуску;
- інформацію про версію коду.

Відтворюваність — властивість **workflow**, а не окремого `.ipynb`.

## 15. Git у науковому моделюванні

Git потрібен не тільки для зберігання коду. Commit дозволяє встановити:

- яка версія моделі дала результат;
- коли змінився параметр;
- чим experiment B відрізняється від A;
- який код використовувався для рисунка у статті;
- чи можна повернутися до попереднього стану.

Рекомендований зв’язок:

> **теза/рисунок/таблиця → experiment ID → config/data → Git commit → code**.

## 16. Очікуваний результат заняття

Ад’юнкт повинен створити і пояснити мінімальний відтворюваний computational modeling project, у якому:

- дані не зашиті в модель;
- параметри не розкидані по notebook;
- результати не редагуються вручну;
- випадковість контрольована;
- є verification;
- є metadata;
- структура придатна для Git;
- можна встановити, за яких умов отримано конкретний результат.

## 18. Головний висновок

**Організоване математичне моделювання — це не файл із кодом, а простежуваний дослідницький процес.**

Python, Jupyter і Git мають забезпечити зв’язок:

> **питання → модель → експеримент → результат → доказ того, як саме цей результат був отриманий.**
