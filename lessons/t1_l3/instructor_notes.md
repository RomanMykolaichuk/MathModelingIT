# Instructor notes — T1.L3

## Головна педагогічна ідея

На цьому занятті не потрібно змагатися в складності формул.

Завдання викладача — змінити уявлення:

> «Я запустив notebook і отримав графік»

на:

> «Я провів ідентифікований, перевірений і відтворюваний computational experiment».

## Рекомендована логіка заняття

### 1. Провокаційне питання

Показати файл:

```text
results_final_v2_fixed_REAL.csv
```

і запитати:

> За якої версії моделі, яких даних, якого seed і яких параметрів отримано цей результат?

Мета — показати проблему traceability.

### 2. Research object ≠ code

Пояснити три рівні:

1. **математична модель** — формальне представлення;
2. **програмна реалізація** — один спосіб обчислення;
3. **експеримент** — конкретні параметри, дані та сценарії.

Це різні сутності.

### 3. Розібрати структуру проєкту

Показати:

```text
data/
src/
notebooks/
tests/
outputs/
config
metadata
```

Запитати, чому `outputs/` не повинен бути джерелом вхідних даних для того самого експерименту.

### 4. Ручний контроль

На дошці:

\[
20+1.8\cdot40-1.2\cdot50=32.
\]

Потім:

```python
deterministic_response(40, 50)
```

Очікування: `32`.

### 5. Config-driven experiment

Показати, що зміна:

```json
"replications": 200
```

не потребує редагування `model.py`.

Поставити питання:

> Чим зміна кількості повторів відрізняється від зміни `resource_gain`?

Перше — дизайн експерименту; друге — параметр математичної моделі.

### 6. Seed

Запустити двічі з `seed=2026`.

Порівняти raw results.

Потім змінити seed.

Пояснити:

- reproducibility не означає, що випадковість зникає;
- seed дозволяє повторити конкретну псевдовипадкову реалізацію.

### 7. Experiment ID

Показати:

```text
t1_l3_0c5d08ed47eb
```

Пояснити, що hash — це не «магічна гарантія науки», а технічний спосіб ідентифікувати config.

Запитати:

> Що станеться, якщо код зміниться, а config залишиться тим самим?

Висновок: потрібен Git commit.

### 8. Outputs

Показати три рівні:

- `results.csv` — raw computational output;
- `summary.csv` — агрегований результат;
- `metadata.json` — умови/ідентичність експерименту.

Не дозволяти вручну «підправляти» результати.

## Контрольні значення

Baseline:

- deterministic response = `32.0`;
- mean observed ≈ `32.2945`;
- std ≈ `4.3768`;
- experiment ID = `t1_l3_0c5d08ed47eb`.

Інші deterministic responses:

- `resource_low` → `14`;
- `resource_high` → `50`;
- `load_low` → `50`;
- `load_high` → `14`.

Звернути увагу:

`resource_high` і `load_low` мають однаковий outcome, але різну причинну структуру.

## Типові помилки

### «У мене є notebook, отже дослідження відтворюване»
Ні. Потрібні дані, dependencies, config і code version.

### «Seed робить результат об’єктивним»
Ні. Seed лише фіксує псевдовипадкову послідовність.

### «Hash доводить, що експеримент правильний»
Ні. Hash лише допомагає ідентифікації.

### «Якщо tests green, модель адекватна»
Tests перевіряють реалізацію конкретних очікувань. Адекватність предметній області потребує validation.

### «Можна відредагувати CSV результатів перед рисунком»
Неприпустимо. Трансформації повинні бути частиною коду.

## Дискусійні питання

1. Чи потрібно комітити `outputs/`?
2. Які outputs є похідними й можуть бути regenerated?
3. Коли великий dataset не варто зберігати в Git?
4. Що важливіше для відтворюваності: notebook чи environment?
5. Чим verification відрізняється від validation?
6. Чи достатньо `requirements.txt` для повної reproducibility?
7. Як пов’язати рисунок у статті з experiment ID?

## Для ад’юнктів

Наприкінці заняття бажано вимагати не абстрактний приклад, а схему власного майбутнього workflow:

```text
my dissertation question
       ↓
source data
       ↓
model
       ↓
config/scenarios
       ↓
experiment
       ↓
verification
       ↓
results
       ↓
figure/table in paper
       ↓
experiment ID + Git commit
```
