# Технічне завдання на мінікниги MathModelingIT

**Статус:** обов’язковий стандарт для всіх мінікниг курсу  
**Каталог:** `books/`  
**Аудиторія:** ад’юнкти та слухачі з різним рівнем математичної і програмної підготовки  
**Мова:** українська  
**Кількість книг:** 11 — по одній на кожне заняття курсу  
**Основний принцип:** проста історія → інтуїція → формалізація → формула → графік → експеримент → межі моделі → Python/Lab → research transfer

---

## 1. Призначення серії

Мінікниги MathModelingIT повинні стати основним теоретичним шаром курсу між коротким lesson `README.md` і практичною інтерактивною лабораторією.

Кожна книга має:

- пояснювати тему значно глибше, ніж поточний lesson README;
- бути самодостатньою для першого знайомства з темою;
- використовувати прості, неопераційні військові приклади;
- поступово вводити математичні позначення;
- містити формули, таблиці, графіки, схеми та короткі Python-фрагменти;
- не перетворюватися на сухий підручник або набір визначень;
- вести читача до конкретної лабораторії та Python-пакета заняття;
- завершуватися перенесенням логіки моделі на власне наукове дослідження.

Мінікнига не замінює lesson package, notebook або лабораторію. Вона повинна пояснювати **чому модель побудована саме так** і **що означає її результат**.

## 2. Авторський стиль

### 2.1. Загальний тон

Стиль — **напівхудожній навчально-аналітичний**.

Текст має читатися як пояснення досвідченого викладача, який розбирає проблему разом зі слухачем, а не як нормативний документ.

Допускаються короткі сюжетні сцени, наприклад:

> Начальник групи планування дивиться на таблицю ресурсів. У нього є чотири варіанти розподілу, але лише два параметри здаються справді критичними. Питання не в тому, який варіант «кращий взагалі», а в тому, що саме ми вважаємо кращим і наскільки стійким буде наш висновок.

Після сюжетного вступу обов’язково виконується перехід до формалізації.

### 2.2. Вимоги до мови

- короткі абзаци;
- одна основна думка на абзац;
- мінімум канцеляризмів;
- термін вводиться спочатку простою мовою, потім формально;
- англійський термін у дужках допускається при першій появі;
- математична формула ніколи не подається без пояснення змісту змінних;
- складне поняття пояснюється щонайменше через один приклад або контрприклад.

### 2.3. Рівень математики

Книга повинна бути зрозумілою слухачеві, який:

- пам’ятає базову шкільну алгебру;
- може читати прості графіки;
- не зобов’язаний володіти вищою математикою на високому рівні;
- може не мати досвіду програмування.

Якщо потрібні похідні, матриці, ймовірності, оптимізація або диференціальні рівняння, вони вводяться від інтуїції до формального запису.

## 3. Військові приклади

### 3.1. Принцип

Військовий контекст використовується для зрозумілості й мотивації, але приклади мають залишатися **навчальними, синтетичними та неопераційними**.

### 3.2. Дозволені типи прикладів

Рекомендовані сюжети:

- розподіл умовного ресурсу між підрозділами;
- планування навчального заходу;
- доставка умовних вантажів між логістичними пунктами;
- резерв часу в підготовці операційного документа;
- вибір умовного технічного рішення за кількома критеріями;
- використання енергетичного, матеріального або часово́го ресурсу;
- планування технічного обслуговування;
- моделювання пропускної спроможності;
- порівняння альтернативних організаційних рішень;
- оцінювання невизначеності параметрів у синтетичному сценарії.

### 3.3. Заборонений рівень деталізації

Не використовувати:

- реальні оперативні плани;
- реальні вразливості;
- точні бойові спроможності;
- координати;
- реальні порядки застосування сил;
- чутливі логістичні маршрути;
- реальні закриті дані;
- конкретні параметри, які можуть мати оперативну цінність.

Усі числові дані повинні бути синтетичними або явно навчальними.

## 4. Обсяг однієї мінікниги

Цільовий обсяг:

- **25–45 екранних сторінок** web-версії;
- орієнтовно **6 000–10 000 слів**;
- **8–15 формул** для тем, де формули є центральними;
- **6–12 графіків/схем/діаграм**;
- **3–6 таблиць**;
- **3–5 коротких Python-фрагментів**;
- **2–4 контрольні мініексперименти**;
- **1 наскрізний військовий сюжет**;
- **1 контрприклад або “злам моделі”**;
- **1 розділ Research Transfer**.

Ці значення є орієнтирами, а не механічною квотою. Для математично насичених тем допускається більша кількість формул і менше сюжетного тексту.

## 5. Обов’язкова структура кожної книги

### 0. Паспорт книги

На початку:

- код заняття;
- назва;
- що читач навчиться розуміти;
- що читач навчиться робити;
- зв’язок із лабораторією;
- зв’язок із Python;
- орієнтовний час читання;
- попередні знання.

### 1. Проблемна сцена

Короткий напівхудожній військовий епізод.

Мета — поставити проблему до введення формул.

Наприкінці сцени повинно прозвучати **дослідницьке питання**.

### 2. Інтуїтивна модель

Пояснити:

- що є об’єктом;
- що змінюється;
- що ми можемо контролювати;
- який результат нас цікавить;
- які фактори поки свідомо ігноруємо.

Тут бажана перша проста схема.

### 3. Від реальної ситуації до математичної моделі

Послідовність:

`Problem → Variables → Parameters → Assumptions → Constraints → Mathematical relation`

Обов’язково показати, **де саме відбувається спрощення реальності**.

### 4. Позначення і формули

Кожна центральна формула подається в чотири кроки:

1. формула;
2. пояснення кожного символу;
3. інтуїтивне прочитання формули словами;
4. короткий числовий приклад.

Наприклад:

[
S(t)=S_0-vt
]

де:

- (S(t)) — залишок ресурсу;
- (S_0) — початковий запас;
- (v) — швидкість витрачання;
- (t) — час.

Після цього текстом:

> Формула говорить дуже просту річ: ми починаємо з певного запасу і в кожну одиницю часу віднімаємо однакову величину.

### 5. Графічна інтуїція

Кожна книга повинна містити графіки, що відповідають ключовим формулам.

Необхідно пояснювати:

- що на осі X;
- що на осі Y;
- що означає форма кривої;
- що означає зміна параметра;
- яку помилку можна зробити, неправильно прочитавши графік.

### 6. Наскрізний військовий приклад

Один приклад проходить через усю книгу.

Структура:

- вихідна ситуація;
- дані;
- формалізація;
- baseline;
- змінений сценарій;
- графік;
- інтерпретація;
- sensitivity;
- limitation.

Він повинен збігатися за логікою з відповідною лабораторією, але не дублювати її дослівно.

### 7. Обчислювальний експеримент

Показати:

- які параметри змінюються;
- що лишається незмінним;
- чому саме такий експеримент дає змістовний висновок;
- який результат очікуємо до запуску;
- який результат отримали;
- що означає різниця.

Обов’язковий елемент:

> **Спробуйте передбачити результат до того, як подивитеся на графік.**

### 8. Python без страху

Не більше 10–20 рядків коду в одному фрагменті.

Код має ілюструвати математичну ідею, а не демонструвати програмістську майстерність.

Для кожного фрагмента пояснити:

- що робить код;
- які рядки відповідають формулі;
- які значення можна змінити;
- який результат потрібно перевірити.

### 9. “Зламай модель”

Обов’язковий розділ.

Читач має знайти:

- граничний випадок;
- неправильне припущення;
- нестійкий висновок;
- помилкову інтерпретацію;
- або параметр, після якого модель стає беззмістовною.

Структура:

`нормальний режим → граничний режим → failure condition → пояснення → можлива модернізація моделі`

### 10. Типові помилки мислення

Не менше трьох.

Приклади:

- «оптимальне» = «найкраще взагалі»;
- кореляція графіків = причинність;
- solver success = глобальний оптимум;
- один ranking = об’єктивна істина;
- середнє значення = гарантований результат;
- модель відтворює дані = модель правильна;
- точні цифри = точна модель.

### 11. Від моделі до лабораторії

Короткий місток:

- що вже зрозуміли;
- що перевірятимемо в Lab;
- які control cases треба отримати;
- що слід спрогнозувати до запуску.

Книга повинна містити пряме посилання на відповідну інтерактивну лабораторію.

### 12. Від Lab до Python

Пояснити різницю:

- browser Lab — швидка інтуїція і керований експеримент;
- Python package — повна реалізація, verification, reproducibility, розширені сценарії.

### 13. Research Transfer

Обов’язково поставити питання:

> Як ця структура моделі може бути використана у моєму дисертаційному дослідженні?

Запропонувати шаблон:

```text
Research question:
Object:
Variables:
Parameters:
Assumptions:
Constraints:
Data:
Method:
Computational experiment:
Verification:
Uncertainty:
Limitations:
Allowed conclusion:
```

### 14. Підсумок на одній сторінці

Формат:

- 5 головних ідей;
- 3 формули/правила;
- 2 типові помилки;
- 1 питання для самоперевірки;
- 1 наступний крок.

## 6. Формули

### 6.1. Формат

Вихідний текст формул — LaTeX/MathJax.

Inline:

`$t_*=S_0/v$`

Block:

```latex
\[
t_* = \frac{S_0}{v}
\]
```

### 6.2. Правила

- не більше двох нових формул поспіль без текстового пояснення;
- кожна нова змінна визначається;
- одиниці вимірювання вказуються, де це доречно;
- формула пов’язується з графіком або числовим прикладом;
- складна формула спочатку пояснюється структурно;
- якщо формула має припущення, вони пишуться поруч.

## 7. Графіки та візуалізації

### 7.1. Мінімальний набір

Книга повинна містити принаймні:

1. одну conceptual diagram;
2. один baseline graph;
3. один scenario comparison;
4. одну sensitivity visualization;
5. один “break the model” visual.

### 7.2. Джерело

Усі числові графіки, де це можливо, генеруються Python-скриптами або notebook-кодом із даних lesson package.

Не малювати вручну графік, якщо існує відповідна математична функція.

### 7.3. Підпис

Кожен рисунок має:

- номер;
- коротку назву;
- 1–3 речення інтерпретації;
- за потреби примітку «синтетичні дані».

### 7.4. Візуальна простота

- один графік — одна головна теза;
- мінімум декоративних елементів;
- достатній контраст;
- не кодувати сенс лише кольором;
- усі осі підписані;
- легенда лише якщо вона справді потрібна.

Книга не дублює notebook.

- завершуватися простою перевіркою результату.

Результати книги, Lab і Python tests не повинні суперечити один одному.

## 12. Джерела і наукова коректність

Книга повинна відрізняти:

- визначення;
- навчальний приклад;
- результат власного computation;
- висновок із джерела;

Для базових математичних фактів достатньо рекомендованої літератури.

Для сучасних методів, де важливий контекст або існують різні підходи, використовуються надійні академічні або офіційні джерела.

Не вигадувати:

- джерела;
- DOI;
- статистику;
- цитати;
- властивості алгоритмів.

## 13. Перевірка математичної коректності

Перед статусом `validated` потрібно:

1. звірити всі baseline values із tests;
2. повторно запустити код, що створює графіки;
3. перевірити одиниці вимірювання;
4. перевірити позначення змінних;
5. перевірити напрям benefit/cost критеріїв, якщо вони є;
6. перевірити всі обмеження задачі;
7. перевірити seed для stochastic examples;
8. переконатися, що текст не робить сильнішого висновку, ніж дозволяє модель.

---

## 14. Педагогічна перевірка

Книга проходить pedagogical review, якщо:

- проблему можна зрозуміти до появи формул;
- кожна формула має словесне пояснення;
- графік можна прочитати без викладача;
- військовий приклад не потребує спеціальних закритих знань;
- є Predict moment;
- є Break moment;
- є Research Transfer;
- читач розуміє, навіщо після книги відкривати Lab;
- книга не перетворюється на довідник Python.

---

## 15. Definition of Done для мінікниги

Мінікнига вважається готовою, коли:

- існують `book.md` і `metadata.yaml`;
- структура відповідає цьому ТЗ;
- є наскрізний синтетичний військовий приклад;
- є формули з поясненнями;
- є потрібні графіки;
- є sensitivity або scenario analysis;
- є “Зламай модель”;
- є типові помилки;
- є Python snippets;
- baseline збігається з lesson tests;
- є місток до Lab;
- є місток до Python;
- є Research Transfer;
- проведено mathematical review;
- проведено pedagogical review;
- усі рисунки відкриваються;
- web build не має битих посилань;
- PDF build, якщо вже увімкнений, не має обрізаного тексту/формул/рисунків.

- **«Теорія»** → відповідна web-версія MiniBook;
- **«Інструкція до лабораторної (PDF)»** → практична PDF-інструкція.

README ніколи не називається «Теорією». Після появи MiniBook кнопка **«Теорія»** повинна вести на її web-версію у новій вкладці.

Цільова послідовність для слухача:

`MiniBook → PDF Lab Instruction → Predict → Run → Explain → Break → Transfer → Python`

Lesson `README.md` залишається технічним паспортом заняття і source-of-truth для структури package, але перестає бути основним навчальним текстом для слухача.

## 18. Порядок розроблення серії

Рекомендований порядок:

1. **T1.L1** — як еталон стилю та структури;
2. **T2.L4** — приклад графової/мережевої книги;
3. **T2.L5** — приклад багатокритеріальної книги;
4. **T2.L1, T2.L2, T2.L3** — Wave 1;
5. **T1.L2, T1.L3, T2.L6** — Wave 2;
6. **T1.L4, T2.L7** — Wave 3.

Після T1.L1 стандарт може бути уточнений, але зміни мають застосовуватися до всієї серії.

## 19. Ключовий принцип серії

Мінікнига має навчати не «підставити числа у формулу», а пройти повний інтелектуальний шлях:

> **побачити проблему → зробити припущення → формалізувати → обчислити → візуалізувати → перевірити → зламати → пояснити межі → перенести метод на власне дослідження.**
